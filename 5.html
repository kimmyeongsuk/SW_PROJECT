지출 예측 가계부 · 구현 기록

5주차 과제

은행 거래내역 명세서(csv)를 업로드해 지출·수입 기록을 일괄 등록하는 기능

은행마다 컬럼명이 다름

은행 예시날짜 컬럼금액 표현 방식
다수 은행거래일시 / 거래일자출금액 / 입금액 컬럼이 분리됨
인터넷전문은행 계열이용일자거래금액 하나 + 입출금구분 컬럼
  1. 은행 유형에 따라 데이터 모델 자체가 다르다 — 오래된 은행 시스템은 "출금/입금"을 완전히 분리된 별도 항목으로 관리하는 반면, 최근 인터넷은행은 "거래금액 하나 + 구분값"으로 단순화해서 관리하는 경우가 많다. 컬럼명뿐 아니라 데이터 구조 자체가 다른 것이다.
  2. 번역/표기 방식 차이 — 같은 의미라도 "거래일시", "거래일자", "이용일자"처럼 은행마다 쓰는 단어가 다르다.

컬럼명 후보 목록 방식

고정된 이름 하나를 찾는 대신, 같은 의미로 쓰이는 여러 이름을 후보 목록으로 만들어두고, 실제 파일의 헤더 중에 후보와 일치하는 게 있으면 그걸 실제 컬럼으로 쓰는 방식 사용 

List<String> dateCols = List.of("거래일시", "거래일자", "이용일자", "날짜", "거래일");
List<String> withdrawCols = List.of("출금액", "출금", "이용금액", "출금(원)");
List<String> depositCols = List.of("입금액", "입금", "입금(원)");
List<String> descCols = List.of("적요", "내용", "가맹점명", "거래내용", "메모");

후보 목록에 이름 하나만 추가하면 된다. 실제로 이 방식으로 바꾸고 나서, 은행마다 다른 형식을 겪을 때마다 리스트에 한 줄씩 추가하는 식으로 대응할 수 있었다.

데이터 구조 자체가 다른 은행

컬럼명 후보만으로는 부족한 경우도 있었다. 일부 은행은 출금/입금 컬럼이 아예 없고, "거래금액" 컬럼 하나에 +/- 부호로 구분하거나, "입출금구분"이라는 별도 컬럼 값("입금"/"출금")으로 구분했다. 그래서 컬럼명 매칭 이후에 구조 자체를 두 가지 형식(A/B)으로 나눠 처리하도록 로직을 확장했다.

형식구조처리 방식
형식 A출금액 / 입금액 컬럼이 분리각 컬럼값을 그대로 읽어 지출/수입으로 저장
형식 B거래금액 하나 + 구분값 또는 부호구분 컬럼이 있으면 그 값으로, 없으면 부호(+/-)로 판단

  • 후보 목록에 없는 새로운 은행 형식을 만나면 여전히 인식하지 못한다. 새 은행을 지원하려면 그 은행의 실제 헤더를 확인하고 후보 목록에 추가해야 한다.
  • 일부 은행 CSV는 인코딩이 EUC-KR이라, 지금 UTF-8 기준 코드로는 한글이 깨질 수 있다. 인코딩 자동 감지 적용해야 함
  • 카테고리는 명세서에 없는 정보라 자동 분류가 불가능해, 전부 "미분류"로 등록한 뒤 사용자가 직접 수정
  • 거래내역서로만 알 수 없는 거래내역들도 있어 OCR 기능이 필요
